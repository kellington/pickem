# Code Review — 2026-07-15 (Claude)

**Scope:** Full codebase review — server (`server/`), domain logic, schema (`shared/`),
Replit auth integration, and client (`client/src/`). ~3,100 lines of TypeScript.
**Reviewer stance:** experienced web developer; suggestions only, no code changed.

---

## Overall impression

For an app built iteratively with the Replit agent, this is in good shape. The
architecture is sensible and several things are done *right*:

- **Schema quality is high.** Unique constraints back up every application-level
  invariant that matters: one pick per member per game, one confidence value per
  member per week, one result per game, one weekly score per member per week
  (`shared/models/pickem.ts:164-190`). Even if application code has bugs, the DB
  can't hold contradictory data. This is the single best defensive decision in
  the codebase.
- **Lock/reveal rules are enforced server-side.** Group picks are filtered by
  kickoff time on the server (`routes.ts:351-360`), not just hidden in the UI.
- **Domain logic is starting to separate cleanly** — `validatePick` and
  `computeStandings` in `server/domain.ts` are pure functions, exactly the shape
  the project conventions call for.
- **Secrets hygiene is fine.** `SECRETS.PRIVATE.YAML` is gitignored and was never
  committed; API keys come from env vars.
- Admin endpoints are all gated on the admin role.

The issues below are mostly about *consistency* (client and server disagreeing
on rules), *bootstrap code left behind*, and *missing tests*. Ordered by
severity.

---

## High priority

### H1. Anyone with a Replit account can join the league
`server/routes.ts:115-125` — when `POST /api/profile` finds no invited
`league_members` match, it **auto-creates an active member** ("first member
becomes admin"). That was bootstrap logic for you; now that the league exists,
any Replit user who finds the URL can log in, complete a profile, and become an
active player auto-enrolled in the season.

**Suggestion:** now that the admin account exists, remove the auto-create branch
and return 403 "Not invited" instead. The invited-email/username matching path
above it is the real membership gate — keep only that.

### H2. "Clear All" can delete locked picks
`server/routes.ts:298-314` — the delete endpoint excludes games whose *result*
is `final`/`in_progress`, but never checks `pickCutoffAtUtc`. Between cutoff and
the first results refresh (i.e., most of the Thursday-night window), a player
can clear a locked pick — effectively dodging a bad pick after lock. The client
(`WeekPicks.tsx:207-211`) filters by cutoff, but the client isn't the authority.

**Suggestion:** apply the same lock rule as `validatePick`: a game is open only
if `pickCutoffAtUtc` is null-safe-checked *and* in the future. (See H3 for the
null case.) Minor: `deleted` counts games iterated, not picks actually deleted.

### H3. Games with no `pickCutoffAtUtc` never lock
`server/domain.ts:30` — the only lock check is
`game.pickCutoffAtUtc && now >= game.pickCutoffAtUtc`. If the cutoff column is
null for any game (bad import, TBD kickoff later scheduled), picks stay editable
forever — including after the game is final. The client has the same assumption.

**Suggestion:** fall back to `kickoffAtUtc` when `pickCutoffAtUtc` is null, and
treat a game with *neither* timestamp as not pickable. Worth a one-off SQL check
that all 272 games in the active season have a cutoff set.

### H4. Client and server disagree on the valid confidence range
Server: `validatePick` caps confidence at `pickableCount` — games *not yet
locked* (`domain.ts:43-48`). Client: the dropdown offers `1..totalGames`
(`WeekPicks.tsx:395`). Once the Thursday game locks, a player who hasn't picked
yet can select 16 in the UI and get rejected ("must be between 1 and 15") — and
players who picked early vs. late face different valid ranges, which also isn't
how confidence pools normally work.

**Suggestion:** validate against the total number of games in the week. The
unique constraint on `(seasonMemberId, weekId, confidenceValue)` plus the
"already used" check handle duplicates; the range shouldn't shrink as games lock.

### H5. Dropped-weeks math zeroes everyone early in the season
`routes.ts:395-400` (and duplicate logic in `domain.ts:130-147`) — the lowest
`droppedWeekCount` (4) weekly scores are always dropped. With ≤4 weeks scored,
*every* week is a "lowest week", so `adjustedTotalPoints` is 0 for all players
until week 5. The home-page standings table displays adjusted points
(`Home.tsx:296`), so the standings will look broken for the first month.

**Suggestion:** only drop `max(0, weeksScored - (totalRegularWeeks -
droppedWeekCount))` weeks — i.e., drops phase in at the end — or simpler, rank
by raw points until more than `droppedWeekCount` weeks are scored. Decide the
rule and record it in DECISIONS.md; either way it needs a unit test.

### H6. No tests, and the test script points at a directory that doesn't exist
`package.json` defines `"test": "tsx --test server/tests/*.test.ts"` but there is
no `server/tests/`. AGENTS.md conventions explicitly call for unit tests on
scoring, confidence validation, dropped weeks, lock/visibility, and standings —
none exist. This is the highest-leverage improvement available: `validatePick`
and `computeStandings` are already pure functions, so testing them needs no DB
mocking. H3, H4, and H5 above are exactly the kinds of bugs those tests catch.

## Medium priority

### M1. Concurrent pick saves can surface raw 500s
`POST /api/picks` validates against a snapshot of existing picks, then writes
(`routes.ts:249-271`). "Pick Favorites" / "Pick Random" fire up to 16 of these
concurrently (`WeekPicks.tsx:170,192`), so two requests can pass validation with
the same state and one then trips the unique constraint → generic 500 "Server
error" in the UI. The DB constraint protects integrity (good), but the UX is a
mystery error.

**Suggestion:** catch the Postgres unique-violation (code `23505`) and return a
friendly 400/409; longer-term, add a batch endpoint (`POST /api/weeks/:id/picks`)
so auto-pick is one validated transaction instead of 16 races.

### M2. `computeStandings` exists but isn't used
The season-standings route re-implements the same drop-week logic inline
(`routes.ts:393-413`) instead of calling `computeStandings` from `domain.ts`.
Two copies of scoring-adjacent math will drift — and only the unused copy is in
the testable module. Use the domain function in the route.

### M3. Repeated boilerplate: admin checks and user/member lookups
The `user → member → role === "admin"` block appears ~8 times, and the
`appUsers`-by-`replitUserId` lookup appears in nearly every route.

**Suggestion:** a `requireMember` middleware that attaches `req.member`, and a
`requireAdmin` built on top. This shrinks `routes.ts` substantially and makes it
impossible to forget a check on a future admin endpoint.

### M4. No transactions around multi-step writes
Examples: profile create + season enrollment (`routes.ts:133-153`), the scoring
loop + week status flip (`routes.ts:433-436`), and especially the
`fix-season-data` cascade of deletes (`routes.ts:791-855`). A failure midway
leaves partial state. Drizzle's `db.transaction(async (tx) => …)` is a small
change for the write paths that matter (scoring, profile setup).

### M5. `fix-season-data` should be retired
It's a destructive one-time production migration (raw cascading deletes) still
mounted as an endpoint and still wired to a button on the home page
(`Home.tsx:353-388`). It's already been run. Leaving destructive one-shot
migrations mounted is how they get run twice under different data. Delete the
endpoint and button; keep the code in git history if you ever need the pattern.

### M6. No request-body validation (zod is installed but unused on the server)
`req.body` is destructured raw everywhere (`routes.ts:226`, `128`, `906`) and
handlers type `req: any`. A string or float `confidenceValue` reaches domain
logic and the DB. You already depend on zod — define input schemas per endpoint
(`z.object({ gameId: z.string(), confidenceValue: z.number().int() })`) and get
typed, validated bodies plus consistent 400s.

### M7. Two parallel user tables
The Replit auth integration upserts login claims into its own `users` table
(`server/replit_integrations/auth/storage.ts`), while your routes upsert the
same claims into `app_users`. Two records per person, updated in two places.
Fine to leave short-term (the integration is vendored), but note it in
DECISIONS.md so nobody later treats `users` as the source of truth.

### M8. Global error handling instead of per-route try/catch
Every route repeats `try { … } catch { console.error; 500 }`. Express 5 forwards
rejected async handlers to error middleware automatically — one
`app.use((err, req, res, next) => …)` handler would remove ~25 try/catch blocks
and give you a single place to log and shape errors (and to map DB constraint
violations per M1).

### M9. `GET /api/me` has write side effects
It creates users, links invited members, and bumps `lastSeenAt`
(`routes.ts:35-66`). It also duplicates the invited-member matching logic from
`POST /api/profile`. Beyond REST purity, React Query refetches this on focus, so
you're doing writes on every tab switch. Suggest: extract the "ensure
user/member" logic into one shared function, and keep member-linking on the
explicit profile/login path.

## Low priority / polish

- **L1. Built `client/dist` is committed.** Three build artifacts are tracked,
  so every deploy churns the diff. If Replit Deployments runs `npm run build`
  (it should), gitignore `client/dist/`.
- **L2. `tsx` at runtime in production** (`start:prod` uses `--import=tsx/esm`).
  Works, but slower boot and no compile-time type gate before deploy. Consider a
  `tsc --noEmit` check in the build step at minimum — right now nothing type-checks
  the server before it ships.
- **L3. All packages in `dependencies`.** Types, vite, drizzle-kit, concurrently
  belong in `devDependencies`. Cosmetic on Replit, but it clarifies what
  production actually needs.
- **L4. Session cookie is `secure: true, sameSite: "none"` unconditionally**
  (`replitAuth.ts:35-40`). Correct for Replit's HTTPS proxy; just be aware
  local-over-plain-HTTP dev logins won't persist a cookie. Conditionalize on
  `NODE_ENV` if local auth ever matters.
- **L5. No standings tiebreaker.** Equal adjusted points get arbitrary ranks
  (`routes.ts:415-416`). Convention in confidence pools is total correct picks
  as the tiebreaker — you already compute `correctPickTotal`.
- **L6. "Score Week" has no completeness guard.** An admin can score and lock a
  week while games are still unplayed (`routes.ts:425-443`). It's re-runnable
  (upserts), so low risk, but a warning when non-final games exist would prevent
  a confusing mid-Sunday lock.
- **L7. Client duplication.** `SpreadMovement` and `formatMl` are copy-pasted in
  `WeekPicks.tsx` and `GroupPicks.tsx`; every page hand-rolls the same
  `fetch`/error pattern; and API responses are typed `any` throughout even though
  `@shared` exports the real types. A tiny `api.ts` helper with typed functions
  would fix all three.
- **L8. Hardcoded "Latest news" array in `Home.tsx:175-179`.** You already have
  the `feature_ideas` table and endpoints — completed ideas could feed this list
  instead of requiring a code deploy per news item.
- **L9. Timezone is hardcoded** as `America/Edmonton` in two client files, while
  the schema has `seasons.leagueTimezone`. Use the season value so the schema
  field isn't dead.
- **L10. Stale draft state in WeekPicks.** After a failed save, the local draft
  merge (`{...serverPicks, ...prev}`, `WeekPicks.tsx:60`) keeps showing the
  rejected pick as selected. The error badge shows, but the selection lies.
  Consider reverting the draft for a game on save error.

## Suggested order of attack

1. **Close the membership hole (H1)** — one small change, real exposure.
2. **Unify lock rules (H2 + H3)** — one shared `isGameLocked(game)` helper used
   by validate, delete, and (mirrored) the client.
3. **Stand up `server/tests/`** — `validatePick` range/lock cases,
   dropped-weeks math (H5 decision), tiebreakers. The script is already wired.
4. **Fix confidence range + dropped-weeks rule (H4, H5)** — with tests from #3.
5. Then the middleware/validation cleanups (M3, M6, M8) as a single refactor
   pass — they touch the same lines, so do them together.

Items 1–4 are small and independent; none require schema changes.
